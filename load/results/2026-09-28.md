# Load test results, 2026-09-28

The first run of the four scenarios in `load/scenarios/` (issue #23), against the production-like stack in `load/docker-compose.yml`, each at the setting in the README and at heavier ones to find where it breaks. Numbers are from k6's summary, `load/sample-metrics.mjs` every 5 seconds, `docker stats`, and `pg_stat_statements` reset before each run.

Common to every run:

- Server: `the-artifact:load` built from `631065a` (v0.4.0), app container limited to 2 CPUs / 2 GB, one Node process. Postgres 17.11 and MinIO (`RELEASE.2026-08-04`) in the same Compose project on the same machine; Postgres started with `pg_stat_statements` for this run (a local override, not in the compose file).
- Settings: `RATE_LIMITS=off`, `CHROME_PATH` on (the image's Chromium), `METRICS_TOKEN=load-test-metrics`.
- Seed: 20 people, 5000 gallery pages in 25 folders, 100 link and 100 organization pages to open of 150 KB (5 files each). One extra set for the storage run: 200 pages to open of 600 KB (120 MB, more than the 64 MB blob cache).
- k6 v1.3.0 on the same machine: an 11-core Mac, Docker with 11 CPUs and 8.8 GB. Before the runs the machine had a load average of 3.4 and was 68% idle, with the dev services (Postgres, MinIO, Mailpit) idle. During the heaviest runs the load average stayed under 7.6 and a sample of the host showed it 80% idle, so k6 wasn't the limit.
- k6 reports p50, p95 and the maximum, not p99. The sampler gives mean S3 time, not a p95.

## Headline

| Scenario | README setting | Sustained | p95 | Breaks at |
| --- | --- | --- | --- | --- |
| Opening pages | 50 VUs, 1 s think | 502 req/s (49 visits/s) | 15 ms | ~2,600 req/s (255 visits/s): 150 VUs without think time pass p95 200 ms on the shell and details |
| Publishing | 5 VUs, 1 s think | 4.5 publishes/s (13 MB/s) | 204 ms | ~22 publishes/s (61 MB/s), p95 1.5 s; the thumbnail queue fills to its cap of 1000 long before |
| Gallery | 30 VUs, 1 s think | 724 req/s (5.4 visits/s) | 98 ms | ~1,200 req/s: 100 VUs without think time fail every threshold (first page p95 775 ms) |
| Thumbnail queue | 100 publishes/min | 76 renders/min | queue max 122 | Anything over ~75 publishes a minute grows the queue; renders run one at a time |

The single Node process is the limit on every read path: it tops out at 1.3 to 1.5 cores of CPU (one JavaScript thread plus GC and I/O threads), and neither more CPUs nor a larger database pool raises that (see Bottlenecks).

### Opening pages, 2026-09-28

- Server: `631065a` (v0.4.0), 2 CPUs / 2 GB, Postgres 17 and MinIO in Compose on the same machine
- Settings: RATE_LIMITS=off, CHROME_PATH on, entry HTML `Cache-Control: private, no-cache` and a view recorded on every open (see below)
- Seed: 20 people, 5000 gallery pages, 100 link and 100 organization pages of 150 KB
- k6: `k6 run -e VUS=50 -e DURATION=3m load/scenarios/open-pages.js`, then `-e THINK=0` with 50 and 150 VUs, from the same Mac

| Measure | 50 VUs, think 1 s | 50 VUs, no think | 150 VUs, no think |
| --- | --- | --- | --- |
| Requests per second (sustained) | 502 (49 visits/s) | 2,625 (255 visits/s) | 2,532 (246 visits/s) |
| p50 / p95 / max, all requests | 3.4 / 15 / 422 ms | 34 / 80 / 493 ms | 109 / 245 / 1,350 ms |
| p95 shell / details / entry / file | 14 / 13 / 11 / 16 ms | 77 / 88 / 65 / 78 ms | 243 / 270 / 192 / 233 ms |
| Failed requests | 0 | 0 | 0 (shell and details p95 thresholds fail) |
| Most VUs before a threshold failed | | 50 passes | 150 fails |
| CPU of the app (cores) | 0.25–0.35 | 1.3 | 1.4 |
| Database queries waiting or running / pool size | up to 26 / 10 | 80–130 / 10 | 290–345 / 10 |
| Event loop lag p99 | 13 ms | 12 ms | 13 ms |
| Memory (RSS) at the end | 296 MB | 341 MB | 361 MB |
| S3 mean | 3 ms (blob cache answers) | 2 ms | 2 ms |
| Thumbnail queue | the 200 pages to open had none: 100 renders in the first 90 s | 0 | 0 |

Experiments at 150 VUs without think time, 1 minute each:

| Change | Requests per second |
| --- | --- |
| None (control, repeated) | 2,432 |
| `APP_CPUS=4` | 2,248 |
| Pool of 40 connections (image rebuilt with `max: 40`) | 1,660 and 1,684 in two runs, app CPU down to 0.9 cores |
| Pages of 600 KB, 120 MB in all (more than the 64 MB blob cache), 50 VUs | 1,538 (97 MB/s), about 390 S3 `GetObject` a second at 1.8 ms mean |

**Views and `Cache-Control: private, no-cache`.** Since the scripts were written the entry HTML is revalidated on every open and each open records a view. k6 has no HTTP cache, so every entry request got the full HTML: that is what a first visit costs, and a browser's repeat visit is a 304 without a storage read. Views are cheap in these runs because the server drops a repeat visitor (address and User-Agent) to the same page within 30 minutes in memory, and k6 sends one address: the default runs wrote about 200 counter rows and 1,364 `artifact_views` rows in total (20 people × 100 organization pages at most). To measure the worst case, the script now takes `UNIQUE_VISITORS=true`, which gives every visit its own User-Agent so every visit by link is counted:

| Measure | 50 VUs, no think, `UNIQUE_VISITORS=true` |
| --- | --- |
| Requests per second | 2,416 (235 visits/s), 8% less than without |
| p95 entry / file | 69 / 83 ms |
| View writes | 19,666 `artifact_view_counts` upserts in 2 minutes: 164 a second, one per visit by link; 99% were HOT updates |
| Upsert time | mean 0.04 ms, max 129 ms (row lock waits on the same 100 counter rows) |
| Postgres CPU | 64% of a core, against 60% without view writes |

What limited it: the app's CPU. Throughput stops at ~2,600 requests a second whatever the VU count, CPU stays at 1.3–1.5 cores whether the container has 2 or 4, and a larger pool makes it slower. The database does little per query (mean 0.01 ms) but a lot of them: every file request reads the page, the version and the file row again (254,119 page lookups for 315,355 requests), and every `/api/config` runs `select id from users limit 1` and a query for SSO connections.

### Publishing, 2026-09-28

- Server, settings and seed as above
- k6: `k6 run -e VUS=5 -e DURATION=3m load/scenarios/publish.js` (500 KB of HTML and 20 files of 100 KB, ~2.8 MB a call), then `-e VUS=20 -e THINK=0 -e DURATION=2m`

| Measure | 5 VUs, think 1 s | 20 VUs, no think |
| --- | --- | --- |
| Publishes per second (sustained) | 4.5 (13 MB/s in) | 21.6 (61 MB/s in) |
| p50 / p95 / max of a publish | 82 / 204 / 389 ms | 837 ms / 1.5 s / 2.9 s |
| Failed requests | 0 | 6 of 2,608 (0.23%), all `write: no buffer space available` in k6 on macOS: the load generator, not the server |
| CPU of the app (cores) | 0.2–0.35 | 0.9–1.25, plus Chromium rendering in the same container |
| Database connections in use / pool size | up to 2 / 10 | up to 28 / 10 |
| Event loop lag p99 | 18–36 ms | 40–105 ms |
| Memory (RSS) at the end | 430 MB | 577 MB (container 705 MB) |
| S3 mean | 38 ms | 132 ms; MinIO at 1.9 cores |
| Thumbnail queue | 66 → 609 in 3 minutes | at the cap of 1000 from the first minute; renders slowed to 36 a minute at 1.4–2.2 s each |

What limited it: the app's CPU and event loop. A publish parses a ~2.8 MB JSON-RPC body, decodes base64 and hashes every file on the one JavaScript thread; at 20 concurrent publishes the event loop lags up to 105 ms, which every other request on the server waits for too. Postgres is idle (publish statements total under 0.5 s in 3 minutes). Thumbnails fall behind at a fifth of this rate.

### Gallery, 2026-09-28

- Server, settings and seed as above; each VU is a plain member of an organization with 5000 pages
- k6: `k6 run -e VUS=30 -e DURATION=3m load/scenarios/gallery.js`, then `-e VUS=100 -e THINK=0 -e DURATION=2m`, then `-e VUS=20 -e THINK=0 -e SCROLL=all -e WITH_THUMBNAILS=false -e DURATION=1m`

| Measure | 30 VUs, think 1 s | 100 VUs, no think | 20 VUs, whole workspace, no thumbnails |
| --- | --- | --- | --- |
| Requests per second (sustained) | 724 (5.4 visits/s) | 1,210 | 389 list pages/s |
| p95 first / scroll / search / folder | 103 / 76 / 134 / 111 ms | 775 / 505 / 781 / 798 ms | 74 / 75 / 79 / 107 ms |
| p95 folder list / thumbnail | 73 / 98 ms | 425 / 630 ms | 58 ms / none |
| Failed requests | 0 | 0 (every duration threshold fails) | 0 |
| Most VUs before a threshold failed | 30 passes | 100 fails | 20 passes |
| CPU of the app (cores) | 0.6–0.8 | 1.35 | 1.1 |
| Database queries waiting or running / pool size | up to 99 / 10 | 520–600 / 10 | up to 35 / 10 |
| Event loop lag p99 | 13–16 ms | 12–20 ms | 15–25 ms |
| Memory (RSS) at the end | 334 MB | 375 MB | 341 MB |
| S3 mean | 5–8 ms | 1–6 ms | 9 ms |
| Thumbnail queue | 230 at the start, draining: opening the gallery queued renders for the pages the publish run left without one | drained | 0 |

Paging through `X-Next-Cursor` costs the same at any depth (p95 75 ms from the first page to the 100th), so the cursor works. The dearest query in `pg_stat_statements` is the folder list with its counts: 1.4 ms mean, 6.6 ms max, once per visit. The card thumbnail-state query reads 50 rows in 0.35 ms. At 5000 pages no query is slow.

What limited it: the app's CPU again. A visit is ~135 requests, almost all of them thumbnails, and each thumbnail request runs five queries (session, organization, page, version, thumbnail) before it answers from the blob cache.

### Thumbnail queue, 2026-09-28

- Server, settings and seed as above; the app restarted first so the queue started empty
- k6: `k6 run -e METRICS_TOKEN=load-test-metrics -e DURATION=5m -e DRAIN=3m load/scenarios/thumbnails.js` (100 publishes a minute of 30 KB pages)

| Measure | Value |
| --- | --- |
| Publishes per second (sustained) | 1.7 (100 a minute), p95 40 ms, none failed |
| Renders | 501 in 8 minutes, none failed, 0.79 s each, 72–84 a minute |
| Thumbnail queue: max, and time to empty | grew ~24 a minute to 122 at the end of publishing, empty ~2 minutes into the drain. Fails `p(95)<100` (114); a 10-minute run would reach ~240 and fail `max<500` near 20 minutes |
| CPU of the app (cores) | 0.05–0.3, Chromium included |
| Memory (RSS) at the end | 196–224 MB |

Under the publish run above, with the app's CPU busy, renders slowed to 1.4–2.2 s and the queue sat at its cap of 1000, so every page published after that has no thumbnail until someone opens the gallery with it.

What limited it: renders run one at a time. The container is idle while they run (under a third of a core), so rendering is bound by the serial queue, not by the machine.

## Bottlenecks and what limits it

1. **One Node process per server.** Every read path stops at the same CPU, 1.3–1.5 cores: ~2,600 requests a second opening pages, ~1,200 in the gallery. Giving the container 4 CPUs instead of 2 changed nothing (2,248 against 2,432 requests a second), because the extra cores have nothing to run. The metric `artifact_db_pool_active` reads 300–600 against a pool of 10 at saturation, which looks like the pool, but it isn't: an image rebuilt with a pool of 40 served 30% less (1,670 requests a second, app CPU down to 0.9 cores), since postgres.js pipelines queries on fewer connections more cheaply. Postgres stays under 0.75 cores with queries of 0.01 ms mean. More throughput needs more processes (a cluster in the image, or documented replicas), and less work per request.
2. **Every request re-reads rows that never change.** A file request reads the page, the version and the file row: 3 queries for immutable data, 150,000–250,000 of each in a 2-minute run. A thumbnail request runs 5. `/api/config`, loaded on every visit, runs `select id from users limit 1` and a query for SSO connections. Caching versions and files in memory, and the setup and SSO state for a few seconds, would cut most of the queries on the hot path and the CPU they cost in the driver and in Drizzle.
3. **Thumbnails render one at a time.** 0.79 s a render caps the server at ~75 new pages a minute; above that the queue grows, and at 1000 it stops queueing. At 20 concurrent publishes, renders also slow to 1.4–2.2 s because Chromium shares the CPU with the requests. The container is under a third of a core busy while rendering, so two or three renders at once would fit.
4. **Large inline publishes block the event loop.** 20 agents publishing 2.8 MB pages push the event loop lag to 105 ms p99 and publishes to 1.5 s p95; the lag is paid by every request on the server, not only the publishes. The JSON parse, base64 decode and SHA-256 of each file run on the main thread. MinIO's time also grows (132 ms mean), but on this machine it shares the CPUs.
5. **View counting is cheap, with one exception.** Counting every visit by link costs 8% of throughput and one HOT update per visit (164 a second at 235 visits a second). The exception is a popular page: all its views update one counter row, and the upsert's maximum was already 129 ms with 100 pages sharing the load. One very busy page would serialize its views on that row lock. Not a limit at these rates.

Not limits here: Postgres (under 0.75 cores, no query over 1.5 ms mean), memory (under 600 MB RSS), object storage for pages that fit in the 64 MB blob cache, and paging deep into the gallery.
